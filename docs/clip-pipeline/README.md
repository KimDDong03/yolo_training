## 1. 개요

### 1.1 목적

부대에 배포된 우리 과 CCTV 프로그램이 이벤트 감지 시 생성하는 **클립(기본 15초 —
트리거 전 5초 + 후 10초, 부대별 설정으로 상이 가능)** 을 수집해 YOLO 탐지 모델의 학습
데이터로 만들고, 재학습한 모델을 다시 CCTV 프로그램에 배포하는 **순환 구조**를 구축한다.

```
[부대 CCTV 프로그램] --배치 내보내기 → 외장하드(월 1회) → 업로드--> [학습 플랫폼(GPU 서버)]
        ^                                                                  |
        |                                                                  v
        +------------------ 개선된 탐지 모델 배포 <---- 평가 게이트 통과 ------+
   (CCTV 감시망과 서버망은 분리 — 이동은 물리 매체. 전 구간 소프트웨어는 우리 과 개발)
```

현재는 이 순환이 없다. 영상을 VLC 로 사람이 수동 추출하고 수동 라벨링하는데, 월
27,000클립(프레임 약 47만 장) 규모가 들어오면 수동 방식은 물리적으로 불가능하다(9절 산정).

### 1.2 범위

- **포함**: **부대 → 서버 클립 전송 체계(업로드 플랫폼)** → 수신·검증 → 프레임 추출 →
  오토라벨링 → 검수 → 데이터셋 편성·분할 → 학습·평가 → 모델 배포까지의 전 과정 설계.
  저장 구조, 명명 규칙, 부대별 관리·평가 체계, 물량·용량·인력 산정, 시스템 배치(Docker
  반입), 구현 로드맵, 타 부서 결정·협조 요청. **네트워크(회선)만 외부에서 구축되고, 그
  위에서 돌아가는 소프트웨어는 전부 이 기획의 범위이며 우리 과가 개발한다.**
- **제외**: 네트워크 회선·서버 하드웨어 자체의 구축(도입 일정·사양 확인만), 학습 알고리즘
  자체(기존 학습 콘솔 기능을 그대로 사용), 데이터관리포탈(별도 운영 중 — 이관 연동만).

### 1.3 개발·요청 구도

- CCTV 프로그램(클립 생성)·**전송 체계(부대 → 서버 업로드)**·이 학습 플랫폼(수신·학습·
  배포)은 **모두 우리 과가 개발**한다. 외부에서 오는 것은 네트워크 회선과 서버·스토리지
  하드웨어뿐이다. 따라서 시스템 사이의 기술 규격([부록 A](interface-spec.md))은 협상
  대상이 아니라 우리가 정해서 각 지점에 직접 구현하는 것이다.
- 이 문서의 **요청 대상은 데이터과**다. 요청의 핵심은 **데이터에 관한 것** — 파일명·구분
  기준 같은 데이터 규격의 확정·승인, 검수 같은 운영 협조, 보존·파기 같은 데이터 정책이다.
  "전체 플로우가 이렇게 진행될 예정이니 이 부분들을 협조해 달라"가 이 문서의 용도다.
  [부록 B](decisions.md)에 항목별로 정리돼 있다. 보안·인프라 판단이 필요한 항목은
  데이터과가 해당 부서로 전달하거나 담당을 지정해 주면 된다.

### 1.4 용어

| 용어 | 정의 |
|---|---|
| 클립 | CCTV 프로그램이 이벤트 감지 시 생성하는 영상 파일 1개 (기본 15초 = 트리거 전 5초 + 후 10초, 부대별 설정) |
| 배치 | 한 부대가 30일치 클립을 모아 한 번에 보내는 전송 단위 |
| 프레임 | 클립에서 설정 간격(기본 1초)으로 추출한 이미지 1장 |
| 프레임 풀(framepool) | 추출된 전체 프레임과 라벨의 보관소. 데이터셋에 편입되기 전 단계 |
| 사건 그룹 | 같은 사건에서 나온 것으로 판정된 클립 묶음. **분할(train/val/test)의 최소 단위** |
| 오토라벨 | 승인된 최신 모델(초기에는 부트스트랩 P-B 의 베이스 모델)로 프레임에 초벌 라벨(박스)을 자동 생성하는 것 |
| 신규성 선별 | 이미 축적된 데이터와 판박이인 장면의 편입을 낮추고 새로운 장면을 우선 편입하는 선별(4.5절) |
| 미탐큐 | CCTV 가 이벤트를 감지했는데 모델이 아무것도 못 찾은 프레임의 검수 대기열 |
| 보류 풀 | 검수 예산이 모자라 이번 달에 검수하지 못한 프레임. 학습에 넣지 않고 보관 |
| 골든셋 | 사람이 전수 라벨한 부대별 고정 평가셋. 배포 합부 판정 전용 |
| 평가 게이트 | 새 모델의 배포 가능 여부를 고정 test 와 골든셋으로 판정하는 절차 |
| 배포 매니페스트 | 모델 파일과 함께 배포되는 메타 문서(클래스 매핑, 버전, 해시 등) |

### 1.5 설계 원칙

1. **기계가 하는 일은 전량, 사람이 하는 일은 예산만큼.** 추출·필터·오토라벨은 전량
   자동이고, 검수는 인력 예산에 맞춰 우선순위가 높은 것부터 한다. 목적은 전량 라벨링이
   아니라 **모델 개선**이다.
2. **부대가 저장·평가·처방의 1차 키다.** 폴더는 부대로 시작하고, 성능은 부대별로 재고,
   처방(데이터 보강)도 부대 단위로 한다(5절). 모델을 부대마다 만든다는 뜻이 **아니다** —
   모델은 부대 유형당 하나(현재는 사실상 1개)이고, 부대 단위인 것은 그 공통 모델에 들어갈
   **데이터의 배합**과 **성적표를 읽는 단위**다(5.4절).
3. **분할은 사건 그룹 단위.** 같은 클립·같은 사건의 프레임이 train 과 val/test 에 갈라지면
   성능이 거짓으로 높게 나온다(4.5절).
4. **버리지 않고 격리한다.** 규격 미준수·해석 불가 데이터는 조용히 버리지 않고 격리 후
   생성 측(부대 장비·CCTV 프로그램) 점검에 반영되도록 회람한다.
5. **모든 자동 판정은 사람이 뒤집을 수 있고, 모든 수치 가정은 시범 배치로 실측 보정한다.**

## 2. 전제와 현황

### 2.1 기존 자산 — YOLO 학습 콘솔 (운용 중)

폐쇄망용 YOLO 학습 웹 콘솔이 이미 있다(FastAPI + React + SQLite, Windows PC, 오프라인
반입 체계). 이 파이프라인은 이 콘솔을 **확장**해서 만든다. 새로 만드는 것과 이미 있는
것의 구분:

| 기능 | 현행 | 비고 |
|---|---|---|
| 데이터셋 등록(zip/폴더), YOLO 형식 해석 | **있음** | 재사용 |
| train/val 분할 | 있음(무작위 비율만) | **test 미지원, 그룹 분할 없음 → 확장 대상** |
| 품질 검사(중복·train/val 누수·클래스 불균형) | **있음** | 3계층 중복 검출 실측 검증 완료. 재사용 |
| 학습 실행·파라미터 추천·시간 예측·스윕·하이퍼파라미터 탐색 | **있음** | 재사용 |
| 학습 실패 진단·오류 유형 분해(TIDE)·라벨 오류 후보 | **있음** | 재사용 |
| 모델 내보내기(ONNX/TorchScript/TensorRT) | **있음** | 재사용 |
| 백그라운드 잡 인프라(GPU 중재 포함) | **있음** | 신규 잡 종류를 등록해 재사용 |
| 영상 처리(프레임 추출) | **없음** | 신규 (P2) |
| 오토라벨링 | **없음** | 신규 (P3) |
| 라벨 박스 편집 검수 화면 | **없음**(열람만 가능) | 신규 (P4) |
| 클립·프레임·배포 이력 관리 | **없음** | 신규 (P1·P6) |

### 2.2 실측으로 검증한 기술 전제

- 콘솔 런타임(현행 Python 3.11.9)에 **OpenCV 4.13.0 + FFMPEG 디코더가 이미 반입돼 있다.**
  H.264 MP4 를 코드로 직접 열어 프레임을 추출할 수 있다 — **추가 반입 소프트웨어 0**.
- ultralytics 8.4.47 은 `model.val(split='test')` 로 **test 셋 평가를 지원**한다
  (설치본 default.yaml 확인). 데이터셋 정의에 test 목록을 등록하면 된다.
- **런타임 파이썬은 보안 지침에 따라 3.14.7 로 고정한다**(개발 PC 에 3.14.7 설치 확인
  완료). 현행 3.11.9 환경에서의 이행 조건 — 네이티브 확장 패키지(torch·opencv·
  onnxruntime-gpu 등)의 **cp314 휠 존재 확인**이 선행돼야 한다. 절차는 10.1 절.
- **CCTV 프로그램 레포 실사 완료** (AI_CCTV_FINAL_VER1): ① 발행 클래스는 COCO 를
  person/animal(bird·cat·dog)/vehicle(car·bus·truck·motorcycle) 3종으로 정규화 — 이
  기획의 **표출 클래스**(7.3 의 2계층 중 운용 표시 단위)와 1:1 정합. 학습 클래스 세분은
  프로그램 표출과 무관하게 병합표로 흡수된다. ② 클립은 MP4 2종(미리보기/증거용) 생성, 이벤트 전후
  버퍼(pre/post ms)는 설정값 — 학습 전달본은 증거용 사용. ③ 클립 매니페스트·사이드카
  체계가 이미 존재(트랙·클래스·신뢰도·bbox 포함) — 부록 A 는 그 확장. ④ 모델은
  **TensorRT `.engine` + 커스텀 헤더**(4바이트 길이 + JSON 메타(클래스명 `names`) + 엔진
  바이너리)로 로드 — 엔진은 GPU 종속이라 현장 빌드로 이 포맷을 만든다(4.8). ⑤ 내부 시각은 epoch
  밀리초, NTP 동기 흔적 없음 — 규격의 시각 동기 요구(감시망 내 NTP 또는 주기 점검) 유지.

## 3. 전체 아키텍처

### 3.1 파이프라인 흐름

```
[부대 CCTV] --(배치 내보내기 → 외장하드 월 1회 → 업로드 도구)--> storage/clips/inbox/<부대>/<배치>/
     |
     v
 (1) 수신·검증 ─ 해시 대조·규격 검사 ──불합격──> quarantine/ (사유 기록, 준수율 리포트 회신)
     |합격
     v
 (2) 클립 등록 ─ 사건 그룹 묶기 · train/val/test 배정(그룹 단위)
     v
 (3) 프레임 추출 ─ 설정 간격(기본 1초) + 무변화 프레임 자동 탈락(디스크에 쓰지 않음)
     v                                            47만 장 → 약 19만 장
 (4) 오토라벨 ─ 최신 승인 모델로 초벌 박스 생성 + 신뢰도 라우팅
     v
     ├── [자동승인]  모든 박스가 확신 구간 → 5% 표본감사만
     ├── [검수큐]    애매한 박스 존재     → 사람이 승인/수정/반려
     └── [미탐큐]    검출 0 또는 이벤트와 불일치 → 사람이 "실제 없음/미탐" 판정 (예산 1순위)
     v
 (5) 검수 ─ 박스 편집 화면. 승인/수정/반려/보류. 모든 행위는 이력으로 남김
     v
 (6) 데이터셋 편성 ─ 승인분만. 불변 스냅샷 버전 생성 + 분포 리포트 + 품질 검사(안전망)
     v
 (7) 학습 ─ 기존 콘솔 기능(추천·예측·스윕·진단) 그대로
     v
 (8) 평가 게이트 ─ 고정 test + 부대별 골든셋. 부대별×클래스별 표. 합부 판정
     |합격
     v
 (9) 배포 ─ 모델 + 배포 매니페스트(클래스맵·버전·해시) 원자 단위 → CCTV 프로그램
                                                                (부대별 배포 가능)
 (원본 클립: 배치 추출 완료 → 데이터관리포탈로 이관 → 확인 후 로컬 파일 삭제.
  우리 저장소에 남는 것은 이미지와 클립 메타데이터뿐)
```

### 3.2 상태 모델

모든 클립과 프레임은 아래 상태를 정확히 하나 가진다. 상태는 DB 에, 진행 로그는 잡별
이벤트 파일에 남는다(기존 콘솔 관례). **모든 처리 단계는 멱등**이다 — 끝난 것은 건너뛰므로
배치 처리가 중간에 실패하면 같은 잡을 다시 돌리는 것이 곧 재처리다.

**클립**

```
received → verified → registered → extracting → extracted → archived
              |            
              └→ quarantined(사유코드)     어느 단계든 실패 시 → failed(단계, 사유)
```

**프레임**

```
extracted → autolabeled → auto_accepted ─┐
                        → review_queue ──┼→ approved | edited | rejected | deferred
                        → miss_queue  ───┘                      (보류)
                                              approved/edited/auto_accepted → in_dataset(버전 참조)
```

(추출 단계에서 무변화로 판정된 프레임은 저장 자체를 하지 않으므로 상태가 없다.)

### 3.3 처리 실패의 처리

| 상황 | 동작 |
|---|---|
| 해시 불일치·사이드카 없음·파일명 규격 위반 | 클립 단위 격리. **배치 전체를 막지 않는다.** 격리 사유는 DB 에 코드로 기록 |
| 디코딩 불가(코덱·손상) | 격리(codec 사유). 규격서에서 MP4/H.264 를 강제하는 근거 |
| 잡 중단(정전·재시작) | 상태 기반 멱등 재실행 — registered 인데 extracted 아닌 클립만 다시 추출 |
| 격리 누적 | 배치별 **규격 준수율 리포트**를 생성해 회람([D-02](decisions.md#d-02)) — 격리 원인의 상당수는 부대 현장 장비 상태(시계 미동기·구버전 프로그램)라 부대 점검 계통과 프로그램 업데이트에 반영하는 것이 목적. 조용히 버리는 일은 없다 |

## 4. 단계별 설계

### 4.1 클립 전송·수신·검증·등록

**전송 체계 — 우리가 만든다. 단, 망이 분리돼 있어 물리 매체를 거친다.** 클립이 저장되는
CCTV 감시망은 별도로 구축된 분리망이라 서버로 직접 전송할 수 없다. 실제 이동은 **외장하드
반출 → 업로드 지점 이동 → 업로드**이고, 월 1회로 예정돼 있다. 그 위의 소프트웨어는 전부
우리 개발 범위다:

```
[CCTV 감시망]                          [서버망]
 CCTV 프로그램의                         업로드 지점 PC 에서
 "배치 내보내기" 기능    --외장하드-->    "업로드 도구" 실행     --> 학습 플랫폼
 (클립+사이드카+매니페스트를  (사람이 월 1회   (배치 폴더를 읽어 클립 단위      업로드 수신 API
  하드에 배치 폴더로 생성)     물리 이동)      업로드·검증·실패분 재시도)      → inbox → ingest
```

- **CCTV 프로그램의 "배치 내보내기" 기능** (I-01): 로컬에 쌓인 클립을 외장하드에 부록 A
  의 배치 폴더 구조(클립+사이드카+manifest.json)로 내보낸다. **매니페스트·해시는 반드시
  이 시점(감시망 안)에 생성한다** — 물리 이동은 네트워크보다 파일 손상·누락 위험이 크고,
  하드에 실린 해시가 있어야 수신 시 "이동 중 무엇이 상했는지"를 판정할 수 있다.
  내보내기 완료 시 하드 검증(재읽기 대조)까지 하고 이동을 시작한다.
- **업로드 도구** (P1): 업로드 지점 PC 에서 외장하드의 배치 폴더를 읽어 학습 플랫폼의
  업로드 API 로 클립 단위 업로드한다. 즉시 해시 검증, 실패분만 재시도, 중복 업로드 멱등
  (같은 하드를 두 번 올려도 안전). 브라우저 웹 업로드 화면은 소량 보충용 보조 경로.
  업로드 지점이 서버에 물리적으로 붙어 있으면 inbox 폴더 직접 복사도 지원한다(업로드
  API 를 거치든 폴더에 놓이든 최종 상태는 같은 inbox 배치 폴더 — ingest 가 동일하게 검증).
- **전송 주기 = 월 1회** (물리 반출이 제약). 배치 = 부대 단위 원칙은 유지 — 하드 하나에
  여러 부대 배치 폴더가 실려도 폴더 단위로 구분되면 된다.
- 하드 용량: 3부대 월 합산 ~190GB — 상용 외장하드 1개로 충분. 반출입 승인·매체 관리
  절차는 보안 규정 확인 대상([D-02](decisions.md#d-02)).

**수신 후 입력**: 부대 단위 배치 폴더 — 클립(mp4) + 클립별 사이드카(json) + 배치
매니페스트(manifest.json). 규격 상세는 [부록 A](interface-spec.md).

**검증 절차** (신규 `ingest` 잡):

1. 매니페스트의 파일 목록·개수·SHA-256 과 실제 수신 파일을 대조한다. 누락분은 재전송
   요청 목록에 기재한다.
2. 클립별로 SHA-256 을 재계산해 사이드카·매니페스트와 대조한다. 불일치 → 격리.
3. 파일명·사이드카 규격 검사(정규식·필수 필드·시각 이상치). 위반 → 격리.
4. **중복 수신 검사**: 클립 정체성 = (부대, 카메라, 이벤트 시각, SHA-256). 동일 해시
   재수신은 조용히 건너뛴다(재전송 안전 — 멱등). 같은 정체성인데 해시가 다르면 둘 다
   보존하고 충돌 표시.
5. 합격 클립을 DB 에 등록하고 내부 키 **clip_id(파일 내용 해시 12자리)** 를 부여한다.
   원본 파일명은 감사 추적용으로 함께 보존한다.

**사건 그룹 묶기와 분할 배정**은 등록 시점에 확정한다(4.5절).

**디스크 사전 점검**: 배치 수신 시작 전에 예상 소요 용량(클립 + 추출 프레임) 대비 디스크
여유를 확인하고 부족하면 시작을 거절한다(월 1회 대량 유입이라 폭주 시점이 예측 가능).

### 4.2 프레임 추출 — 기존 VLC 수동 방식의 대체

| | 기존 (VLC 수동) | 신규 (파이프라인 내장 자동) |
|---|---|---|
| 노동 | 사람이 클립마다 조작 | 수신되면 자동. 월 27,000클립 배치 처리 |
| 간격 | 씬필터 설정에 의존, 부정확 | 설정값(기본 1초, 0.2~5초)으로 정확히 |
| 출처 추적 | 파일명에 계보가 남지 않음 | `클립ID_t시각.jpg` — 어느 클립의 몇 초인지 영구 보존 |
| 중복 정리 | 추출 후 별도 수작업 | 추출과 동시에 무변화 프레임 자동 탈락 |
| 필요 소프트웨어 | VLC 별도 설치 | 콘솔에 이미 반입된 OpenCV 사용 — **추가 반입 0** |

**동작** (신규 `extract` 잡):

- 클립을 열어 설정 간격의 프레임만 디코딩한다(중간 프레임은 건너뛰어 비용 절약).
  fps 는 파일 헤더가 아니라 사이드카 값을 우선한다(헤더가 깨진 파일 대비).
- **무변화 필터**: 직전에 유지한 프레임과 지각 해시(dHash, 기존 품질 검사 코드 재사용)를
  비교해 임계(해밍 거리 ≤ 4, 설정값) 이하면 탈락시킨다. **탈락 프레임은 디스크에 쓰지
  않는다** — 9절 용량 산정의 전제. CCTV 고정 카메라 특성상 작은 물체의 이동을 해시가
  못 느낄 수 있으므로 임계 기본값은 보수적으로 두고, 시범 배치에서 "탈락분 표본을 사람이
  확인"해 임계를 보정한다.
- **연속 클립의 시간 겹침 처리**: 객체가 계속 있으면 클립이 이어서 생성되고, 후속 클립의
  pre 구간이 직전 클립의 post 와 **같은 시간대를 다시 담는 경우가 실제로 있다**(개발
  담당 확인, 2026-08-27 — 항상은 아니고 겹칠 때가 있음). 그래서 추출·필터는 클립 단위가
  아니라 **사건 그룹 내 절대 시각 기준**으로 한다: 프레임의 절대 시각(= event_ts −
  pre_ms + 클립 내 오프셋)이 같은 그룹에서 이미 추출된 시각과 겹치면 건너뛰고, 무변화
  dHash 비교도 클립 경계를 넘어 그룹 연속으로 이어 간다. (같은 장면이 두 클립에서 두 번
  추출되는 것을 원천 차단 — 겹치지 않는 클립에는 그대로 무해)
- 저장: JPEG 품질 85, 원본 해상도 유지(원거리 소형 객체 — 해안 부대 보트 등 — 를 위해
  다운스케일하지 않는다). 파일명 `{clip_id}_t{밀리초:05d}.jpg`.
- 클립 단위 원자성: 클립의 프레임 폴더가 완성된 뒤에만 클립 상태를 `extracted` 로 바꾼다.

**재추출 경로**: 원본 클립은 배치 추출이 끝나면 데이터관리포탈로 이관되고 로컬에서
삭제된다(6.4절). 간격을 바꿔(예: 1초 → 0.5초) 다시 추출하려면 **포탈에서 해당 클립을
재수령**해야 하므로, 포탈의 조회·재수령 지원 여부가 확인 항목이다([D-05](decisions.md#d-05)).
간격 변경 실험(시범 배치)은 이관 전 로컬에 있는 동안 하는 것이 효율적이다.

### 4.3 오토라벨링과 신뢰도 라우팅

**동작** (신규 `autolabel` 잡, GPU — 기존 잡 인프라의 GPU 중재를 그대로 사용해 학습과
충돌하지 않는다):

- 지정한 모델(기본: 초기 부트스트랩 P-B 에서 재학습한 베이스 모델, 이후 매 사이클 최신
  승인 모델)로 필터 통과 프레임 전량을 추론한다. 약 19만 장 기준 GPU 로 2~3시간(9절).
- 결과는 YOLO 텍스트 라벨(프레임 풀에 저장) + 박스별 신뢰도 기록.
- **클래스 번호 규칙**: 프레임 풀의 라벨은 항상 **전역 클래스 번호**로 저장한다.
  추론 모델이 부대 유형 프로파일(7.3절)로 학습된 모델이면, 그 모델의 배포 매니페스트에
  있는 클래스 매핑으로 변환한 뒤 저장한다. 어떤 모델(가중치 해시)과 어떤 설정으로
  라벨했는지가 프레임마다 남는다 — 나중에 "그 세대 모델이 못 보던 것" 을 추적하는 근거.

**신뢰도 3단 라우팅**:

| 큐 | 조건 (기본값, 설정 가능) | 처리 |
|---|---|---|
| 자동승인 | 모든 박스 신뢰도 ≥ 0.60 이고 0.25~0.60 구간 박스 없음 | 라벨 채택. 5% 무작위 표본감사만 |
| 검수큐 | 0.25~0.60 구간 박스가 하나라도 있음 | 사람이 승인/수정/반려 |
| 미탐큐 | 검출 0건, **또는** 이벤트의 기대 객체 미검출(예: 사람 감지(`PERSON`) 이벤트인데 사람 미검출) | 사람이 "실제 없음(배경)" vs "미탐 → 박스 작성" 판정 |

(혼재 주의: 한 클립·한 프레임에 사람·차량·동물이 **함께 나오는 것은 정상**이고 탐지
학습에 오히려 좋은 데이터다. 위 "불일치"는 **기대 객체가 안 잡혔는가**만 보는 검사이며,
기대 밖 객체가 추가로 검출되는 것은 불일치가 아니다 — 그 박스들은 신뢰도에 따라 일반
라우팅을 탄다. 동시 감지 클립의 기대 객체는 사이드카의 `event_types` 목록 전체다.)

**미탐큐가 이 설계의 핵심 장치다.** 오토라벨의 근본 위험은 자기강화 — 모델이 못 잡는
것은 라벨도 안 되고, 그 데이터로 또 학습하면 미탐이 영구화된다. 그런데 우리 클립은
**CCTV 가 이벤트를 감지해서 만든 것**이다. 이벤트가 났는데 모델이 아무것도 못 봤다면
미탐일 확률이 높다. 이 외부 신호(이벤트 트리거)가 자기강화 고리를 깨는 유일한 지렛대이므로
미탐큐는 검수 예산에서 **1순위**로 배정한다(4.4절).

**미탐큐는 트리거 상대 위치와 사건 맥락으로 세분화한다.** 클립은 트리거 전 5초(pre) +
후 10초(post)로 구성되고(부대별 설정 — 사이드카의 pre_ms 로 프레임별 상대 위치 계산),
객체가 계속 있으면 클립이 **이어서** 생성돼 한 사건이 여러 클립이 된다. 그래서 "pre 는
무검출이 정상"은 **사건 그룹의 첫 클립에서만** 참이다 — 후속 클립의 pre 는 직전 클립에서
추적되던 시간이라 검출이 이어지는 게 정상이다. 무검출 프레임을 전부 같은 미탐큐로
취급하면 큐가 부풀어 검수 예산을 삼키므로, 다음처럼 가른다:

| 무검출 프레임의 위치·맥락 | 해석 | 우선순위 |
|---|---|---|
| **사건 중간의 깜빡임** — 같은 그룹에서 앞뒤 프레임엔 검출이 있는데 이 프레임만 무검출 (후속 클립 pre 의 무검출 포함) | **추적 단절** — 객체가 연속 존재하는 게 문맥상 확실한데 놓친 프레임. 미탐 확률 최대 | **최상** |
| 트리거 부근 (±2초, 설정값) 무검출 | 트리거 순간인데 무검출 — 비정상(모델 세대 차이 등) | 최상 |
| **그룹 첫 클립**의 pre 구간, 트리거에 가까운 순 | **조기 탐지 후보** — 접근 중인 객체를 아직 못 잡던 프레임일 확률 최대. 라벨해 학습하면 **탐지 시점 자체가 앞당겨진다** (pre 버퍼의 존재 이유이자 이 순환 구조의 핵심 이득) | 상 — 트리거 직전부터 역순 검수 |
| 그룹 첫 클립 pre 초입 · 그룹 마지막 클립 post 후반 | 객체 미등장/이탈 — 대부분 배경 | 하 — 샘플만 |

(후속 클립의 pre 에서 검출이 정상적으로 이어지는 프레임은 무검출이 아니므로 이 표와
무관하게 일반 라우팅을 탄다.) 이 구조 때문에 **무검출 프레임 비율은 9절 가정(15%)보다
높게 나올 가능성이 크다** — 세분화 덕에 예산은 상위 구간에만 쓰이므로 파이프라인은
감당하지만, 시범 배치에서 위치별 무검출 분포를 실측해 우선순위 경계(±2초 등)를 보정한다.

자동승인의 잔여 위험: 신뢰도가 높아도 **누락**(찾은 박스는 맞지만 못 찾은 물체가 있음)은
신뢰도로 드러나지 않는다. 그래서 자동승인분에도 5% 표본감사를 두고, 매월 유지 프레임
전체의 1~2%를 오토라벨을 보지 않은 **블라인드 전수 라벨** 표본으로 만들어 오토라벨 자체의
정밀도·재현율을 측정한다(12절 리스크 1).

**오탐·미탐 신고 클립의 특별 취급**: CCTV 프로그램은 운용자 조작으로 **오탐 확정 클립**
(`FP_REPORT` — 이벤트가 났지만 운용자가 오경보로 기각)과 **미탐 신고 클립**(`MISS_REPORT`
— 모델이 경보하지 않은 상황을 운용자가 수동 저장)을 만들 수 있다(부록 A 8절, 구현은
I-01). 이 신호는 위 라우팅의 "추정"을 "확정"으로 바꾸므로 우선 처리한다:

| 신고 유형 | 정체 | 처리 |
|---|---|---|
| `MISS_REPORT` | 하드 포지티브 — 모델이 지금 못 하는 것의 직접 증거 | 미탐큐 **최상위** 직행 → 박스 작성 → train 편입 시 **오버샘플 배율 적용**(기본 ×2~3, 설정값) |
| `FP_REPORT` | 하드 네거티브 — 모델을 속인 배경(그림자·수풀 등) | 간이 확인 후 배경(negative) 예시로 **우선 사용** — 오경보 감소에 직효. train 의 0~10% 배경 상한(4.6절) 안에서 |

가중 방식에 대한 결정: **손실(loss) 가중이 아니라 오버샘플링으로 한다.** 학습 프레임워크가
이미지별 손실 가중을 지원하지 않아 내부 수술이 필요한 반면, 같은 샘플을 k회 편입하는 것이
기대값 기준 등가이고 분포 리포트로 통제·확인 가능하다. 주의 두 가지 — ① 배율은 **train
에만** 적용한다(val/test 는 자연 분포 유지, 분할도 해시 규칙 그대로 — 오류 클립을 train
에 강제 배정하면 test 가 쉬워져 점수가 부푼다. 어차피 약 70%는 자연히 train 에 떨어진다).
② 배율은 보수적으로 시작해 평가 게이트로 효과를 확인하며 조정한다 — 오류 데이터 쏠림은
학습 분포를 현재 모델의 실패 모드 쪽으로 왜곡해 전체 성능을 해칠 수 있다.

### 4.4 검수

**검수 화면** (신규 — 이 파이프라인에서 가장 큰 신규 UI):

- **필름스트립 열람**: 프레임 낱장이 아니라 클립 단위로 유지 프레임 5~10장을 한 화면에
  펼친다. 연속 프레임의 박스는 거의 같으므로 클립 단위 일괄 판정이 낱장 판정보다 몇 배
  빠르다. 인력 산정(9.3절)은 이 방식을 전제로 한다.
- **박스 편집기**: 박스 그리기·이동·크기 조절·클래스 변경·삭제. 기존 콘솔의 박스 표시
  컴포넌트를 렌더링에 재사용하되 편집 상호작용은 신규 개발.
- **판정**: 승인(라벨 그대로 채택) / 수정 승인(고쳐서 채택) / 반려(학습 제외) / 보류.
- **감사 추적**: 모든 검수 행위는 누가·언제·무엇을 어떻게 바꿨는지 이력 테이블에
  추가 기록된다(덮어쓰지 않음). 되돌리기의 근거이자 보안 감사 자료(12절 리스크 4).

**물량 대응 — 검수 예산제**: 전수 검수는 월 약 293시간(≈ 59인일)이 들어 비현실적이다
(9.3절 산정). 대신 검수 가용 시간을 예산으로 두고 우선순위대로 소진한다:

1. **미탐큐 전량** (약 90h) — 위 4.3절의 이유로 최우선.
2. **자동승인 표본감사** (약 6h).
3. **검수큐 우선순위 샘플링** (남는 예산) — 우선순위 점수 = 불확실성(신뢰도가 경계
   중앙에 가까움) + 희소 클래스 포함 + 커버리지 부족분(야간·저성능 부대([5.4절](#54-부대별-처방-루프))·신규 카메라).
4. 예산이 소진되면 나머지는 **보류 풀** — 자동승인하지 않고, 학습에도 넣지 않는다.
   다음 달 예산 여유가 있거나 특정 취약점(예: 특정 부대 야간 성능)이 발견되면 그 조건으로
   보류 풀을 재조회해 검수한다(사후 능동학습).

**학습에 들어가는 것은 자동승인 + 승인 + 수정 승인뿐이다.** 보류·반려는 들어가지 않는다.
(이 자격은 필요조건이고, 실제 편입은 4.5 절의 신규성 선별을 한 번 더 거친다 — 고정
카메라의 반복 장면이 데이터셋을 부풀리는 것을 막기 위해서다.)

검수 인력 규모는 [D-03](decisions.md#d-03) 결정 사항이다. 2명 기준 시나리오는 9.3절.

### 4.5 데이터셋 편성과 분할

**왜 프레임 무작위 분할이 안 되는가**: 같은 클립에서 1초 간격으로 뽑은 프레임들은 서로
거의 같은 사진이다. 이걸 무작위로 나누면 train 에서 본 장면이 val/test 에 다시 나와
성능이 거짓으로 높게 나온다(데이터 누수). 현행 콘솔의 품질 검사가 바로 이런 누수를 잡는
기능인데, 애초에 만들지 않는 것이 옳다.

**분할 단위 — 사건 그룹**: 클립 단위로도 부족하다. 이벤트 재감지로 한 사건이 클립 여러
개로 쪼개져 들어오면 근접 중복이 클립 경계를 넘는다. 그래서:

- 그룹 키 우선순위: ① 사이드카의 `incident_id`(사건 상관 ID) — CCTV 프로그램도 우리 과
  개발이므로 연속 재감지에 같은 ID 를 붙이는 발급 기능을 직접 구현한다(부록 B I-01).
  ② ID 가 없는 클립(구버전 프로그램·과도기)은 **같은 카메라에서 이벤트 시각 간격 10분
  (설정값) 이내로 이어지는 클립 = 한 그룹**. ②는 휴리스틱이다 —
  화각이 겹치는 카메라 쌍으로 신고된 조합([D-10](decisions.md#d-10))은 같은 시간 창을
  한 그룹으로 묶는 보정을 넣는다.
- 한 그룹의 모든 프레임은 반드시 같은 스플릿(train 또는 val 또는 test)에만 들어간다.

**배정 방식 — 결정적 해시 제안 + 저장값이 진실**:

```
버킷 = blake2b("{그룹키}|{seed}") % 1000
버킷 < 100        → test   (기본 10%)
버킷 < 300        → val    (기본 20%)
그 외             → train  (기본 70%)
```

- 비율은 **설정 가능**하고(그룹 개수 기준 — 그룹이 월 수천 개라 프레임 수 비율 오차는
  ±1~2% 수준), 배정 결과는 DB 에 저장되어 **저장된 값이 진실**이다. 해시는 신규 그룹의
  기본 배정을 정하는 제안자일 뿐이다.
- **한번 배정된 그룹은 절대 옮기지 않는다.** 특히 test 는 영구 홀드아웃 — 새 배치가
  들어와도 기존 test 구성이 변하지 않아야 "지난달 모델 vs 이번 달 모델" 비교가 성립한다.

**층화 보정 — 클래스·조건 균형**: 해시 배정은 그룹 수가 많으면 클래스·주야·부대 비율을
자연히 비슷하게 맞추지만, **희소 클래스**(해안 부대의 보트·튜브처럼 등장 클립이 적은
클래스)는 우연히 한쪽에 몰릴 수 있다. 대응:

1. 배치 편입 시 **분포 리포트**를 반드시 생성한다: 클래스×스플릿, 주/야×스플릿,
   부대×스플릿 인스턴스·이미지 수 표(기존 클래스 불균형 검사의 확장). 임계 이탈 시 경고.
2. 희소 클래스가 val/test 에 결핍이면 **이번 배치의 신규 그룹에 한해** 그 클래스를 포함한
   그룹을 결핍 스플릿으로 재배정한다. 이미 배정된 그룹은 건드리지 않으므로 test 영구성과
   충돌하지 않는다.
3. 배포에 반드시 필요한 클래스가 test 나 골든셋에 아예 없으면 경고가 아니라 **평가 게이트
   불합격**으로 처리한다(4.7절).

(참고: 외부 도구 — scikit-learn 의 층화 분할, Roboflow 등 — 는 쓰지 않는다. 폐쇄망
반입·외부 서비스 제약도 있지만, 그쪽 도구는 "증분 배치 + 영구 test" 요구와 맞지 않는다.
그룹 제약 분할은 직접 구현이 소규모다.)

**test 이중화 — 해시 test 와 골든셋**:

| | 해시 홀드아웃 test | 부대별 골든셋 |
|---|---|---|
| 생성 | 그룹의 10% 자동 배정, 매달 누적 | 부대별 수작업 선별(야간·악천후·원거리 포함) |
| 라벨 | 오토라벨+검수 라벨 | **사람 전수 라벨(오토라벨 미적용·미노출)** |
| 용도 | 월별 성능 추이 관찰 | **배포 합부 판정** |
| 규모 | 자동 | 부대당 500~1,000장, 온보딩 시 구축, 반기 보강 |

이중화가 필요한 이유: 오토라벨을 거친 test 라벨은 오토라벨 모델의 미탐 편향을 공유한다.
"모델이 원래 못 보는 것"은 test 정답에도 빠져 있으므로 그 test 점수는 그 결함을 못 잰다.
배포 판정은 사람이 만든 골든셋으로만 한다. 골든셋 구축 인력은 [D-04](decisions.md#d-04).

**같은 카메라의 반복 장면 — 편입 신규성(다양성) 선별**: 고정 카메라는 화각이 같고 이동
루트·복장도 반복되므로, **서로 다른 클립·다른 날짜에서도 매우 비슷한 이미지가 계속
생긴다.** 구분이 중요하다 — 배경이 같아도 객체의 위치·거리·자세가 다르면 **유효한 학습
예시**다(모델이 배우는 것은 객체다. 같은 배경의 반복은 그 카메라의 오검출을 줄이는 데도
기여한다). 문제는 ① 객체 배치까지 사실상 같은 장면의 반복과 ② 특정 카메라·구도로의
편중이다. 이는 기존 3겹 방어(클립 내 무변화 필터 → 사건 그룹 내 절대 시각 중복 제거 →
빌드 후 품질 검사)를 **통과한다** — 사건이 다르니 그룹이 다르고, 픽셀 동일이 아니니 중복
임계에도 안 걸린다. 그래서 편입 단계에 4번째 층을 둔다:

1. **신규성 점수 — 비교 대상은 "이번 배치"가 아니라 "지금까지 축적된 전체"다**: 자격
   (자동승인·승인·수정 승인)을 갖춘 프레임이라도 전량 편입하지 않고, **누적 편입분 전체
   (초기 부트스트랩 P-B 의 기존 5만 장 포함)** 중 같은 카메라 프레임들과의 유사도 —
   이미지 임베딩(기존 품질 검사의 임베딩·캐시 재사용) **과** 객체 배치(클래스·박스 위치
   구성) 조합 — 가 모두 높으면 편입 우선순위를 낮춘다. 배경만 같고 박스가 다르면
   통과한다. 배치 내부끼리만 비교하면 "이번 달엔 새롭지만 작년 축적분과 판박이"인 장면이
   계속 들어오므로, 반드시 누적 기준이어야 한다.
   - **비교 범위는 같은 카메라로 한정한다** (전 카메라 교차 비교는 하지 않는다 — 결정):
     반복되는 배경·구도는 그 카메라의 고정 화각에서 나오므로 중복의 사실상 전부가 같은
     카메라 안에서 생기고, 다른 카메라의 비슷해 보이는 장면은 중복이 아니라 **다른 장소의
     정당한 다양성**이라 눌러내면 안 된다. 교차 비교는 계산량만 키운다. (카메라 교체로 새
     번호를 받으면 인덱스도 새로 시작 — 새 장비·각도의 장면은 다시 샘플링할 가치가 있어
     의도된 동작)
   - 구현: 편입 프레임의 임베딩을 **카메라별 누적 인덱스**로 유지하고 신규 후보를 그
     인덱스에 대조한다. 기존 품질 검사의 계층 구조(dHash 로 후보를 좁히고 임베딩으로
     확정)와 캐시를 재사용 — 카메라 단위로 쪼개면 대조 규모는 수만×수만 수준(초 단위).
2. **유사 묶음은 대표만, 시기 분산으로**: 같은 장면 묶음에서 대표 N장(기본 2~3장,
   설정값)을 계절·조명이 퍼지도록 뽑아 편입하고, 나머지는 풀에 보관한다(버리지 않음 —
   추후 재선별 가능).
3. **카메라별 편입 쿼터**: 부대별 쿼터(5.4)와 같은 메커니즘을 카메라 축으로도 적용하고,
   분포 리포트에 카메라×스플릿 편입량을 표시해 편중을 드러낸다.

**데이터셋 버전 = 불변 스냅샷**: 버전 생성 시 이미지(하드링크 — 디스크 추가 0)와 라벨
(사본 — 월 40MB 수준이라 무시 가능)을 버전 폴더 안에 고정한다. 이후 검수로 프레임 풀의
라벨이 바뀌어도 **과거 버전은 변하지 않는다** — "그 모델이 정확히 무슨 데이터로 학습됐나"
가 영구히 재현 가능하다(감사·비교의 전제). 재검수 반영은 새 버전 생성으로만 한다.
확정된 버전은 읽기 전용이며 콘솔의 이미지 삭제·수정 기능이 거부된다(정리는 프레임 풀에서
하고 새 버전으로).

**카메라 단위 분할은 하지 않는다**: 학계 관행으로는 "새 카메라에 일반화되는가"를 재기 위해
카메라째로 홀드아웃하기도 하지만, 이 모델은 **학습에 쓴 바로 그 카메라들에 재배포**된다.
배경 암기는 우리 운영 도메인에서는 결함이 아니라 이점이다. 다만 부대 확장 시 "새 카메라
일반화"를 알아야 하므로, 부대 유형별 1대를 **진단용 카메라 홀드아웃**(학습 제외)으로
지정해 그 지표만 따로 관찰한다. 잔존 위험: 화각이 겹치는 두 카메라가 같은 사건을 찍으면
시점이 달라 중복 검출로는 안 잡힌다 — incident_id 발급(부록 B I-01)·중첩 신고(D-10)로 줄이되, 완전히
없앨 수는 없음을 명시해 둔다.

**품질 검사는 안전망으로 유지**: 그룹 분할이 지켜지면 기존 누수 검출은 침묵해야 정상이다.
발화하면 그룹 규칙(간격 G, 중첩 표)의 실패 신호로 해석해 규칙을 보정한다. 누수 검사는
train/val 2자 비교에서 **train/val/test 3자 비교로 확장**한다(test 오염도 안전망 안으로).

### 4.6 학습

기존 콘솔 기능을 그대로 쓴다 — 파라미터 추천, 소요 시간·메모리 예측, 시간 예산 학습,
한 축 비교(스윕), 하이퍼파라미터 탐색, 실패 진단, 오류 유형 분해(TIDE), 라벨 오류 후보.
파이프라인이 데이터셋 버전을 만들면 콘솔에서 그 버전을 선택해 학습하는 흐름이다.

**배경(negative) 이미지 정책** — 객체가 없는 배경 이미지도 학습에 넣어야 오검출이 준다
(YOLO 권장: train 의 0~10%). 이 파이프라인의 규칙:

- **공급원**: ① 미탐큐에서 사람이 "실제 없음"으로 확정한 프레임 ② `FP_REPORT` 클립
  (운용자가 기각한 확정 오탐 — 최상급) ③ 표본감사 중 발견된 빈 프레임. 클립은 무언가가
  이벤트를 울렸을 때만 생기므로 이 배경들은 전부 **감지기를 속인 장면**(그림자·수풀·야간
  노이즈)이다 — 무작위 빈 사진보다 오검출 감소 효과가 크다(하드 네거티브).
- **사람 확정 없이 배경으로 넣지 않는다.** 모델이 못 찾은 프레임을 자동으로 배경 처리하면
  그 안의 진짜 미탐을 "아무것도 없음"으로 가르쳐 **미탐을 강화**한다. 검출 0건은 반드시
  미탐큐의 사람 판정(장당 약 3초)을 거친다.
- **상한 0~10%**: 배경 과다는 양성 예시를 희석해 재현율을 해친다. 확정 배경이 상한을
  넘으면 `FP_REPORT` 출신 우선 + 카메라·시간대 다양성으로 선별한다.
- 구현: 배경 프레임 = **빈 라벨 파일**(YOLO 관례). 배경도 사건 그룹 분할을 그대로 따라
  val/test 에 자연히 포함되어 오검출 평가(TIDE 배경 항목)에 기여한다.

### 4.7 평가 게이트

새 모델을 배포해도 되는지의 판정 절차. **선언이 아니라 실행 가능한 형태로 정의한다**:

- **평가 대상**: ① 고정 test (`split='test'` 명시 평가 — 2.2절에서 지원 확인)
  ② 배포 대상 부대의 골든셋.
- **리포트**: 두 평가 모두 **부대별×클래스별** 지표 표(mAP50·재현율)를 포함한다.
  전체 평균은 부대 하나의 성능 저하를 가린다(5절).
- **합부 기준의 구조** (수치는 [D-12](decisions.md#d-12)에서 확정):
  1. 필수 클래스 목록과 클래스별 최저선(예: 사람 재현율 하한) — **표출 클래스 기준**
     (학습 세분 클래스 지표는 진단용, 7.3절)
  2. **부대별 최저선** — 미달 부대가 있으면 전체 불합격 또는 해당 부대만 배포 보류
     (부대별 배포가 가능하므로 정책 선택지가 있다 — D-12)
  3. 직전 승인 모델 대비 허용 하락폭
  4. test 와 골든셋 **모두** 통과해야 합격
  5. 필수 클래스가 test/골든셋에 없으면 불합격, 평가 실행 오류도 불합격
  6. 적용한 기준의 버전을 판정 결과와 함께 기록
- **기록**: 판정 결과(지표·합부·근거 리포트·기준 버전)는 배포 이력(deployments)에 남는다.

### 4.8 모델 배포

- **배포 단위 = 모델 파일 + 배포 매니페스트, 원자 배포.** 매니페스트 내용: 모델 파일
  해시, 학습 데이터셋 버전, 부대 유형 프로파일 ID, **모델 출력 번호 ↔ 전역 클래스 번호
  매핑표**, 권장 신뢰도 임계값, 평가 게이트 결과 참조, 대상 부대 목록.
- 클래스 매핑표가 필수인 이유: 부대 유형 프로파일(7.3절)에 따라 모델의 출력 번호가
  다르다. 모델 파일만 배포하면 수신측이 번호를 오해석할 수 있다. CCTV 프로그램의
  매니페스트 해석은 우리 과 구현 사항(부록 B I-01)이고, 부대까지의 전달 경로·적용 주기는
  [D-11](decisions.md#d-11) 결정 사항이다.
- **배포 정본은 ONNX 다 — TensorRT 엔진은 부대 현장에서 빌드한다.** TensorRT 엔진은
  빌드한 GPU 의 아키텍처와 TRT 버전에 종속되는 산출물이라(빌드 = 그 GPU 에서의 커널
  튜닝), 학습 서버에서 빌드한 엔진을 GPU 가 다른 부대 PC 에 배포하면 동작을 보장할 수
  없다. 그래서:
  - 배포 패키지의 모델 = **ONNX(GPU 중립) + 매니페스트**. P6 패키징은 ONNX 산출물에
    매니페스트를 묶는다.
  - **CCTV 프로그램이 모델 교체 시 자기 GPU 에서 엔진을 1회 빌드해 캐시**한다(수 분,
    I-01) — 프로그램에 이미 실린 TRT 8.x 로 빌드하므로 **TRT 버전 불일치도 원천 소멸**.
    빌드 산출물에 실사로 확인한 커스텀 헤더(4바이트 메타 길이 + JSON `names` + 엔진)를
    적용해 기존 로딩 경로를 그대로 쓴다.
  - 예비 카드: 현장 빌드가 부담스러운 환경이 나오면 TRT 하드웨어 호환 모드(Ampere 이후
    공통 엔진, 성능 일부 손실)를 검토한다. 부대 PC 의 GPU 기종 실사는 [D-10](decisions.md#d-10).
  - 클래스맵이 매니페스트와 엔진 메타 양쪽에 실려 이중 검증되는 구조는 유지. 신뢰도
    임계값은 프로그램의 `confidenceThreshold` 설정으로 전달(권장값을 매니페스트에 기재).
- 프로그램의 ReID 모델(사람/차량 재식별)은 이 파이프라인의 범위 밖이다 — 탐지 모델만
  다룬다.
- 사이드카의 `model_version`(그 클립을 만든 배포 모델)이 다음 달 배치에 실려 돌아오므로,
  "모델 세대별로 무엇을 놓쳤는가"를 추적할 수 있다 — 순환 구조의 효과 측정.

## 5. 부대(unit) 축 설계

부대는 이 시스템의 **저장·평가·처방의 1차 키**다. 전체 평균만 보면 "3개 부대 평균은
좋은데 특정 부대만 나쁜" 상태를 놓친다. 부대마다 카메라·배경·거리·조명·객체 분포가
다르므로 관리도 부대 단위여야 한다.

### 5.1 물리 구조 — 모든 경로가 부대로 시작한다

6.1절 폴더 트리 참조. 수신함·격리함·프레임 풀 모두 1차 폴더가 부대다. 배치도 부대
단위로만 받는다(여러 부대 혼합 배치 불허 — 매니페스트에 부대 명시). 효과:

- 부대 단위 백업·포탈 이관·보존 연한 관리·파기가 폴더 단위 작업이 된다.
- 특정 부대 데이터에 문제(오염·보안 이슈)가 생기면 부대 단위로 격리·중단할 수 있다.
- 부대별 용량·유입량 모니터링이 폴더 집계로 끝난다.

### 5.2 부대별 test 와 골든셋

- 해시 배정은 부대와 무관하게 그룹의 10%를 test 로 두므로, **부대별 test 물량이 자동
  확보**된다(부대당 월 약 900클립분). 별도 부대별 test 를 만들 필요 없이, 평가를 항상
  부대 슬라이스로 집계하면 된다.
- 골든셋은 **부대별로** 구축한다(부대 유형별이 아니라 — 같은 해안 유형이라도 부대마다
  카메라·배경이 다르다). 부대당 500~1,000장, 신규 부대 온보딩의 필수 단계(5.5절).

### 5.3 부대별 평가 리포트

평가 게이트 리포트(4.7절)와 월별 추이 대시보드에 **부대별×클래스별 표**를 필수로 둔다:

| (예시) | 사람 | 차량 | 동물 | 보트 | 부대 종합 |
|---|---|---|---|---|---|
| A부대 (내륙) | 0.91 | 0.88 | 0.79 | — | 0.86 |
| B부대 (내륙) | 0.93 | 0.90 | 0.82 | — | 0.88 |
| C부대 (해안) | 0.87 | 0.85 | 0.74 | **0.61** | 0.77 |

위 예시라면 "C부대 보트" 가 처방 대상으로 바로 드러난다. 전체 평균(0.84)만 보면 놓친다.

### 5.4 부대별 처방 루프

월 사이클: 배치 수신 → 처리 → 부대 슬라이스 평가 → **다음 달 조정**. 저성능 부대에 대한
레버, 시도 순서대로:

1. **원인 진단 먼저** — 그 부대의 미탐큐 비율, 오류 유형 분해(TIDE), 주야·클래스 분포,
   **카메라 해상도**(최소 640 보장이지만 카메라별 상이 — 저해상도 카메라의 원거리 객체는
   정보량 자체가 적어 모델이 아니라 화질이 한계일 수 있다)를 본다. 데이터 **양**이 아니라
   **분포·화질**이 원인일 수 있고, 처방이 달라진다.
2. **그 부대 검수·편입 쿼터 상향** — 검수 우선순위 산식(4.4절)에 부대 가중치 항이 있어,
   저성능 부대의 프레임이 검수 예산을 더 가져가게 한다. 보류 풀에서도 그 부대 조건으로
   재조회해 추가 편입한다.
3. **데이터셋 빌드의 부대별 샘플링 배율** — 버전 생성 시 부대별 오버/언더샘플 배율을
   설정할 수 있게 한다(예: C부대 ×2). 분포 리포트가 반영 결과를 표시한다.
4. **(예비) 부대 전용 파인튜닝 모델** — 배포가 부대 단위로 가능하므로(4.8절) 전역 모델
   + 특정 부대 파인튜닝의 2단 구성도 열려 있다. 다만 모델 수가 늘면 평가·배포·추적 비용이
   부대 수에 비례해 커지므로 **기본 비권고**, 1~3으로 안 풀릴 때의 예비 수단.

### 5.5 부대 온보딩 절차 (확장 대비)

부대 추가는 예정된 일이므로 절차를 미리 못 박는다:

1. 부대 코드 발급(7.2절 코드 대장) 및 부대 유형(내륙/해안 등) 분류 → 클래스 프로파일 결정
2. 카메라 목록·설치 위치·**화각 중첩 쌍** 신고 접수(D-10)
3. 규격 시범 배치 1회 수신 → 준수율 리포트 회신, 문제 해소
4. **부대 골든셋 구축**(사람 라벨 500~1,000장) — 이것 전에는 그 부대에 대한 배포 판정 불가
5. 정규 편입 개시 → 첫 평가에서 부대 슬라이스 확인, 필요시 처방 루프 가동

## 6. 저장 구조와 데이터 관리

### 6.1 폴더 트리

```
storage/
  clips/
    inbox/<부대>/<배치ID>/          # 수신 원본 (클립 + 사이드카 + manifest)
    processed/<부대>/<yyyymm>/      # 추출 완료, 데이터관리포탈 이관 대기 (이관 확인 후 삭제)
    quarantine/<부대>/<배치ID>/     # 규격 미준수·손상 (사유는 DB)
  framepool/
    images/<부대>/<카메라>/<yyyymm>/<clip_id>/<clip_id>_t01000.jpg
    labels/<부대>/<카메라>/<yyyymm>/<clip_id>/<clip_id>_t01000.txt
  datasets/<데이터셋ID>/            # 버전 스냅샷 (기존 콘솔 구조 + data/ 에 하드링크·라벨 사본)
  runs/<실행ID>/                    # 학습 결과 (기존 콘솔 구조 그대로)
```

- `images ↔ labels` 대칭 구조는 기존 콘솔·YOLO 관례와 같아서 라벨 해석·품질 검사 코드를
  수정 없이 재사용한다.
- `<yyyymm>` 층은 월 단위 보존·파기 정책(6.4절)을 폴더 작업으로 만들기 위한 것이다.
- 프레임 풀과 데이터셋 폴더는 **같은 볼륨**에 둔다(하드링크 전제 — 4.5절 불변 스냅샷).
- 경로 길이는 Windows 260자 제한 안에 든다(최심 경로 실측 약 120자).

### 6.2 DB 확장 (기존 콘솔 SQLite 에 테이블 추가)

| 테이블 | 주요 컬럼 | 역할 |
|---|---|---|
| batches | 배치ID, 부대, 수신 시각, 매니페스트, 클립 수(정상/격리), 상태 | 배치 수신 이력·준수율 |
| clips | clip_id, 배치, 부대, 카메라, 이벤트 시각·유형·점수, **pre_ms·post_ms**(트리거 상대 위치 계산용), SHA-256, 길이·fps·해상도·코덱, 트리거 모델 버전, **사건 그룹 ID**, **split**, 상태, 격리 사유, 이관 시각 | 클립 원장. 분할 배정의 진실 |
| frames | frame_id, clip_id, 시각 오프셋, 경로, 지각 해시, 상태, 라우팅, 박스 수·신뢰도 요약, **오토라벨 모델(가중치 해시·설정·클래스맵)**, 검수 시각·행위 | 프레임 원장 |
| review_actions | frame_id, 행위, 변경 전/후, 행위자, 시각 | 검수 감사 추적 (추가만, 수정 없음) |
| deployments | 배포ID, 대상 부대, 모델 해시, 데이터셋 버전, 매니페스트, **평가 게이트 결과·기준 버전**, 배포 시각 | 배포 이력. "무엇으로 판정해 내보냈나" |

**프레임에는 사이드카 파일을 만들지 않는다** — 클립의 사이드카는 수신 때 한 번 파싱돼
clips 행이 되고, 추출 때 프레임마다 생기는 **frames 행이 이미지의 메타데이터 저장소**다
(클립 메타는 clip_id 연결로 전 프레임에 상속 — 카메라·트리거 상대 위치·사건 그룹이 조인
한 번으로 나온다). 중복 제거·선별·큐·분할은 전부 이 DB 행을 기준으로 동작한다. 이미지별
json 파일 수십만 개는 파일시스템·백업·집계에 부담만 되고, 선별·큐는 본질적으로 집계
쿼리라 DB 가 맞다(7.1 "판정 기준 = DB 메타" 원칙의 프레임판).

규모: frames 는 월 약 19만 행(유지분만), 연 230만 행 — 현행 SQLite(WAL)로 충분하다.
부대 10개 이상으로 확장되면 재평가한다(12절 리스크 10).

### 6.3 이미지 저장 방식

이미지는 **파일시스템(서버에서는 영속 볼륨)** 에 두고 DB 에는 메타데이터만 둔다.
DB 안에 이미지 바이너리를 넣는 방식은 쓰지 않는다 — YOLO 학습이 파일 경로를 요구하고,
수십만 장 바이너리는 DB 백업·성능을 망가뜨린다.

### 6.4 원본 클립·프레임의 생애 주기

| 대상 | 정책 |
|---|---|
| 원본 클립 (파일) | 배치 추출 완료 → `processed/` 대기 → **데이터관리포탈로 이관**(별도 운영 중인 포탈 — 확정 방침) → 이관 확인(가능하면 해시 검증) 후 **로컬 파일 삭제**. 우리 저장소에 클립 파일은 남지 않는다. 이관 방식·재수령 지원은 [D-05](decisions.md#d-05) |
| 원본 클립 (메타) | **DB 의 clips 행은 영구 보존** — 프레임 계보·사건 그룹·분할 배정·감사 추적의 근거라 지우면 안 된다(행당 수백 바이트). 포탈 이관 참조(이관 시각·포탈 식별자)를 함께 기록 |
| 격리 클립 | 준수율 리포트 회람([D-02](decisions.md#d-02))·원인 종결 후 삭제 |
| 프레임(미편입) | 보류·반려분 포함 프레임 풀에 보존 — 사후 능동학습 재료. 보존 연한·파기 절차는 D-05 (월 폴더 단위 파기 가능) |
| 프레임(편입) | 데이터셋 버전이 참조하는 동안 유지. 버전 폐기 정책도 D-05 와 연동 |
| 학습 결과(runs) | 월 5~10회 학습 × 회당 0.5~2GB — 반기마다 불합격 실험분 정리(승인 모델의 근거 run 은 영구 보존) |

## 7. 명명 규칙 · 코드 대장 · 클래스 체계

### 7.1 파일·ID 명명 규칙

| 대상 | 규칙 | 예 |
|---|---|---|
| 클립 파일명 (CCTV 측 생성) | `{부대코드}_{카메라ID}_{YYYYMMDD}T{HHMMSS}_{이벤트코드}_{일련4}.mp4` — ASCII 대문자, KST | `U003_CAM07_20260801T221304_PERSON_0012.mp4` |
| 사이드카 | 클립과 동일 이름 `.json` | `U003_..._0012.json` |
| 검증 정규식 | `^U[0-9]{3}_CAM[0-9]{2,3}_[0-9]{8}T[0-9]{6}_[A-Z]{2,12}_[0-9]{4}\.mp4$` | 수신 검증에 사용 (부록 A 와 동일 — 확장자는 소문자) |
| clip_id (내부 정본 키) | 파일 내용 해시(blake2b) 앞 12자리 16진수 — 동일 파일 재수신을 ID 차원에서 감지 | `3fa2b1c9d0e4` |
| 프레임 파일명 | `{clip_id}_t{밀리초:05d}.jpg` — 계보(어느 클립의 몇 초)가 파일명에 영구 보존 | `3fa2b1c9d0e4_t01000.jpg` |
| 배치 ID | `{부대코드}-{YYYYMM}-{일련2}` | `U003-202608-01` |
| 데이터셋 버전명 | `clips-{범위}-{YYYYMM}-r{판}` | `clips-all-202609-r1`, `clips-U003x2-202609-r1` |

- 파일명은 사람 디버깅용 중복 표기이고, **정본 메타데이터는 사이드카 JSON**이다(부록 A).
  시각의 정본도 사이드카의 시간대 포함 표기이며 파일명은 KST 로 통일한다.
- 같은 초에 클립이 2개 이상 생기면 일련번호로 구분한다.
- 파일명이 규격을 어기면 수신 시각+내용 해시로 자동 명명해 **격리**한다(버리지 않는다).
- 원본 파일명은 DB 에 보존한다(감사 추적). 내부 폴더·참조는 clip_id 를 쓴다 — 사람의
  탐색은 화면의 부대·카메라·기간 필터가 담당한다.
- **판정의 기준은 파일명이 아니라 DB 메타다** (원칙): 파일명·사이드카 해석은 수신 시점의
  ingest 한 곳에서만 하고 결과를 DB(clips·frames)에 저장한다. 이후의 모든 로직 — 카메라별
  신규성 비교, 사건 그룹, 분할, 절대 시각 계산 — 은 DB 를 조회하며 파일명을 다시 파싱하지
  않는다. 파일명·폴더 구조는 사람용(디버깅·복구·파기 편의) 보조 표기다. 규격이 바뀌어도
  ingest 파서 한 곳만 고치면 되는 구조를 유지한다.

### 7.2 코드 대장 (레지스트리) — 우리 과가 관리

파일명과 메타데이터에 쓰이는 코드는 전부 대장으로 관리한다. 코드가 흔들리면 폴더·통계·
분할이 전부 흔들리기 때문에, 발급·폐기는 대장 갱신으로만 한다.

| 대장 | 형식 | 규칙 |
|---|---|---|
| 부대 코드 | `U` + 3자리 (U001~) | 신규 부대 온보딩(5.5절) 시 발급. 재사용 금지 |
| 카메라 ID | `CAM` + 2~3자리 | **부대 내 유일**(전역 식별은 부대+카메라 조합). 교체 시 신규 번호 |
| 이벤트 코드 | 대문자 영문 2~12자 | 실사로 확인한 발행 클래스와 정렬해 확정(부록 A 8절). 예: `PERSON`, `VEHICLE`, `ANIMAL` — 미탐큐 라우팅(4.3절)이 이 코드에 의존 |
| 클래스 번호 | 아래 7.3절 | append-only |

### 7.3 클래스 체계 — 2계층 사전(학습 ↔ 표출) + 부대 유형 프로파일

- **사전은 2계층이다 — 학습은 세분(fine), 표출은 통합(coarse)**:
  - **표출(운용) 클래스 — 확정**: `사람 / 차량 / 동물` (+해안: `튜브 / 보트`). CCTV
    화면·이벤트에 보이는 단위이고, 프로그램의 발행 클래스(2.2 실사)와 1:1 이다.
  - **학습 클래스 — 초안, [D-07](decisions.md#d-07) 협의로 확정**: 승용차와 전차, 멧돼지와
    조류처럼 시각적으로 이질적인 것을 한 클래스로 묶으면 모델이 넓은 경계를 배워야 해서
    양쪽 다 어중간해진다. "화면에서 판정 가능하고 운용상 의미 있는" 수준까지 세분해
    학습하고, 표출은 병합표(학습→표출)로 만든다 — **병합은 추론 후 매핑이라 공짜, 분리는
    재라벨 캠페인이라 비싸다. 그래서 세분은 처음(P-B 라벨링 전)에 확정해야 한다.**

    | 표출 | 학습 클래스 초안 |
    |---|---|
    | 사람 | 사람 (세분 없음) |
    | 차량 | 차량-일반(승용·트럭·버스), 차량-군용(전차·장갑차 등), 차량-미상 |
    | 동물 | 멧돼지, 고라니, 조류, 동물-기타 |
    | 튜브 / 보트 (해안) | 세분 없음 |

  - **"-미상" 클래스 장치**: 야간·원거리에서 "차량인 건 확실한데 종류 불명"인 박스는
    `차량-미상`으로 라벨한다 — 억지 판정의 라벨 노이즈를 막으면서 표출 수준 정보는 온전히
    학습에 쓴다. 검수 속도 유지의 핵심 장치.
- **전역 번호는 학습 클래스 수준에서 append-only** — 추가만 하고 재사용·재배열하지 않는다.
  프레임 풀의 모든 라벨은 이 전역(학습) 번호로 저장된다(4.3절).
- **부대 유형 프로파일**: 표출 클래스 집합 기준 — 내륙 = {사람, 차량, 동물}(에 속한 학습
  클래스 전부), 해안 = {+ 튜브, 보트}. 데이터셋 버전 생성 시 프로파일로 필터·리매핑한
  학습 설정을 만들고, 모델 출력 번호 ↔ 전역 번호 매핑과 **학습→표출 병합표**는 배포
  매니페스트에 실린다(4.8절) — CCTV 화면은 병합표를 거쳐 "차량"으로만 표출한다.
- **평가 게이트의 합부는 표출 클래스 기준이다**(운용 성능 = "차량으로 잡혔는가").
  학습 클래스별 지표는 진단용 — 특히 희소한 학습 클래스(예: 전차가 월 수 건)는 데이터가
  쌓일 때까지 지표가 불안정하므로 합부에 걸지 않고 관찰만 한다(4.7절과 연동).
- **추가 분리**(예: 차량-일반 → 승용/트럭)는 재라벨 대상이다. 해당 클래스가 있는 프레임만
  검수큐로 재소환하는 "재라벨 캠페인"으로 범위를 한정한다.
- 부대별 내륙/해안 분류는 코드 대장 작성 시 함께 기록한다(작성: 우리 과).

### 7.4 라벨링 기준서 — 검수 일관성의 뿌리

같은 장면을 검수자마다 다르게 판정하면 데이터가 서로를 상쇄한다. 검수 시작(P4 가동) 전에
**라벨링 기준서**를 만들어 검수 화면 옆에 두고, 골든셋 라벨도 같은 기준서를 따른다.
담을 것:

- 클래스별 정의와 예시 사진(맞는 예/틀린 예/애매한 예)
- 경계 사례 판정 규칙: 원거리 객체의 최소 크기(몇 픽셀부터 라벨하나), 부분 가림 시 박스
  범위(보이는 부분만 vs 추정 전체), 야간 실루엣·열상 판정, 겹친 군집의 개별/묶음 처리,
  유리·수면 반사, "애매하면 어느 쪽으로" 의 기본 방향
- 개정 절차: 검수 중 나온 애매 사례를 기준서에 판례처럼 추가하고 판 번호를 올린다.
  기준이 크게 바뀌면 영향 클래스만 재라벨 캠페인(7.3) 대상인지 판단한다.

**아직 확정되지 않았다 — 검수 시작(P4·P-B 검수) 전 반드시 확정할 항목** (담당: 우리 과):

- [ ] 원거리 객체의 최소 라벨 크기 (몇 픽셀부터 라벨하는가)
- [ ] 부분 가림 시 박스 범위 (보이는 부분만 vs 추정 전체)
- [ ] 야간·저조도 실루엣의 판정 기준
- [ ] 겹친 군집(다수 인원 등)의 개별/묶음 처리
- [ ] 유리·수면 반사, 모니터 속 화면의 처리
- [ ] 판단 불가 프레임의 기본 방향 (제외 vs 보류)
- [ ] 클래스별 정의문과 예시 사진 세트
- [ ] **학습 클래스 세분 목록 확정(D-07 협의)과 "-미상" 판정 규칙** — 어느 수준까지
  구분하고, 구분 불가 시 어떻게 라벨하는가

## 10. 시스템 배치와 반입 (Docker)

### 10.1 확정 방향

- **접속 형태는 웹(브라우저)이다.** Docker/k8s 서버 운영과 다중 검수자 요구에서 웹이
  사실상 유일한 답이다 — 검수자 PC 에 설치·배포·업데이트가 없고(폐쇄망에서 프로그램
  방식은 PC 마다 반입·설치를 반복해야 한다), 업데이트는 서버 이미지 반입 1회로 끝나며,
  GPU 작업은 어차피 서버에서 돈다. 현행 콘솔이 이미 웹이라 전환 비용도 없다.
  (확인 사항: 검수자 PC 의 표준 브라우저 — D-08 에 포함)
- **플랫폼은 기존 학습 콘솔을 코어로 확장한다** — 이 기획 자체가 콘솔을 "수집→검수→학습
  →배포 통합 플랫폼"으로 개편하는 것이다. 신규 재개발·기성품 도입과 비교해 결정했다:

  | 선택지 | 평가 |
  |---|---|
  | **기존 콘솔 코어 확장 (채택)** | 잡 인프라·GPU 중재·실측 검증된 품질검사·학습/진단/내보내기·테스트 302개를 그대로 재사용. 신규 개발은 파이프라인 고유 부분에 집중 |
  | 플랫폼 신규 재개발 | 위 검증 자산의 재구현+재검증에 수개월. 얻는 것이 불명확 — 기각 |
  | CVAT 도입(검수 UI 대체) | 어노테이션 UI 는 성숙하나 컨테이너 8~10개 스택(DB·캐시 등)의 반입 심사·운영 부담이 크고, 우리 검수 큐·부대 축과의 연동 글루 개발이 별도로 필요 — 기각 |
  | Label Studio 도입(검수 UI 대체) | 경량이지만 연동 글루는 동일하게 필요하고 필름스트립·미탐큐 흐름을 살릴 수 없음 — **1차 기각, 퇴로로 유지**: 검수 인력이 5인 이상으로 늘거나 편집 UX 요구가 자체 구현 범위를 넘으면 재검토 |

  파이프라인의 차별 요소(사건 그룹 분할·부대 축·평가 게이트·격리 규격)는 기성품에 없어
  어차피 자체 개발 대상이다. 기성품이 확실히 앞서는 것은 박스 편집 UI 하나이므로, 1차는
  자체 구현(P4)하고 위 퇴로를 남긴다.
- **구현 언어는 파이썬이다** (검토 후 결정): 핵심인 학습·튜닝·진단이 ultralytics/PyTorch
  (파이썬 전용 생태계) 위에 있어 ML 코어의 언어 선택권은 사실상 없다. 주변부(웹·잡 관리)만
  다른 언어(Go·C# 등)로 분리하는 안은 기각 — 런타임이 2개가 되어 폐쇄망 반입·심사 면적이
  늘고, 층간 프로세스 통신이 생기며, 검증된 기존 백엔드(테스트 302개)를 버리게 된다.
  성능 우려는 해당 없음 — 무거운 일(디코딩·해시·추론·학습)은 OpenCV/CUDA 네이티브 코드가
  수행하고 파이썬은 조율만 한다(실측: 품질검사 2,689장 27초, 오토라벨은 GPU 병목).
  부대 배포 경계는 언어 중립 포맷(ONNX/TensorRT)이라 CCTV 프로그램의 언어를 구속하지
  않는다. 그리고 각 처리 단계가 독립 워커(파일+DB 로만 연결)라, 특정 단계가 실측 병목이
  되면 **그 워커의 내부만** 컴파일된 외부 도구로 교체하면 되고 나머지는 영향이 없다
  (예: 부대가 늘어 추출이 느려지면 extract 워커 속만 ffmpeg 프로세스 호출 + GPU 하드웨어
  디코딩으로 교체 — 입출력이 같아 다른 단계는 변경 0). 언어 선택이 통째로 되돌려야 하는
  결정이 아니라는 뜻이다.
- **런타임 파이썬 3.14.7 고정** (보안 지침): 운영 Docker 이미지와 개발 PC 트랙 모두
  3.14.7 로 통일한다(개발·운영 버전 이원화 금지). 이행 절차 — ① 인터넷 가능 환경에서
  전 의존성의 **cp314 휠 존재 확인**(torch 2.11+cu128·ultralytics·opencv·onnxruntime-gpu
  — 순수 파이썬 패키지는 무관) ② 미지원 패키지는 버전 상향 ③ 번들·이미지 재구성 후
  기존 테스트 302개로 검증. **파이프라인 신규 개발 착수 전에 이행**한다 — 기존 테스트가
  이행 검증기가 되고, 신규 코드가 처음부터 3.14 기준이 된다.
- **운영 형태**: 도입 예정 리눅스 GPU 서버(**H200 × 16장 확정**)에 **Docker 이미지로
  반입**, Kubernetes 단일 Pod + 영속 볼륨(PV). 데이터(클립·프레임 풀·데이터셋·DB)는 전부
  컨테이너 밖 PV(21TB 스토리지)에 둔다. GPU 는 16장 중 **학습 플랫폼 할당분**을 쓴다 —
  이 파이프라인의 상시 수요(월 배치 처리 수 시간 + 학습·탐색)는 1~2장으로도 충분하고,
  다중 GPU 학습(DDP)은 기존 콘솔이 이미 지원하므로 할당이 늘면 그대로 활용된다. 서버가
  공용이라면 할당·스케줄 정책은 [D-08](decisions.md#d-08). **서버 내부 구성(볼륨 배치·
  Pod 구조·네임스페이스)은 우리 과가 설계한다** — 외부에서 확정된 제약은 리눅스·k8s·
  Docker 뿐이다(2026-08-27 확인).
- **DB 는 SQLite 단일 인스턴스** — DB 의 선택·구축은 기술 구현 사항으로 우리 과가
  결정한다(데이터과 접점은 DB 가 아니라 데이터다 — 명명·분류 표준은 D-01, 보존·파기는
  D-05, 현황 보고는 D-01-4 로 질의해 두었고, 표준이 제시되면 필드 명명에 반영한다).
  검토 후 SQLite 유지를 결정했다: 이 규모(frames 연 230만 행,
  동시 사용자 검수자 수 명 + 워커)에서 WAL 모드로 충분하고, 기존 콘솔·테스트가 이 위에
  있어 이행 비용이 0 이며, 별도 DB 서버 컨테이너는 반입 심사 면적과 운영 부담만 키운다.
  Pod 복제(replica) 금지를 배포 문서에 명시하고, 전환 재검토 조건(부대 10개 이상 또는
  검수 동시성 급증)은 12절 리스크 10 에 둔다. (CCTV 프로그램 내부의 PostgreSQL, 데이터
  관리포탈의 DB 는 각자 별개 시스템 — 학습 플랫폼과 무관)
- **다중 검수자**를 위해 서버 이행 시 **로그인·권한(인증) 신설이 필수**다. 현행 콘솔은
  로컬 단일 사용자 전제(무인증)라 그대로 서버에 올리면 안 된다. 검수 행위자 기록
  (review_actions)도 인증이 있어야 의미가 있다. 방식은 [D-08](decisions.md#d-08).

### 10.2 이행 순서 — 기능 먼저, 이식은 서버 도입 시점에

1. **1단계 (지금~서버 도입 전)**: 파이프라인 기능(11절 P1~P5)을 현행 콘솔 코드베이스에서
   구현·검증한다. 현행 PC 로도 월 배치 처리가 성능상 가능하다(오토라벨 19만 장 2~3h,
   추출은 하룻밤). 시범 배치 실측도 이 단계에서 한다.
2. **2단계 (서버 도입 시)**: 컨테이너화·이식 + 인증 신설. Windows 의존 코드는 지금부터
   프로세스 제어 모듈에 격리해 두어 이식 범위를 좁힌다.

### 10.3 리눅스 이식 요구사항 (구현 수용 기준)

- **프로세스 종료**: 워커를 프로세스 그룹으로 기동하고, 종료 전 **신원 대조(PID + 프로세스
  시작 시각 + 그룹 ID 를 저장해 두고 대조) 후에만 그룹 종료**한다. PID 만 믿고 죽이면
  재사용된 PID 의 무관한 프로세스를 죽일 수 있고, 그룹 종료는 그 피해가 그룹 전체로
  커진다. (현행 Windows 구현은 이미 신원 대조를 한다 — 같은 수준을 리눅스에서 보장)
- **컨테이너 수용 시험**: 리눅스 컨테이너 안에서 ① 잡 시작·강제중지·재시작·GPU 재배정
  ② `model.val(split='test')` ③ OpenCV 로 실클립 디코딩 — 전부 통과해야 이행 완료.
- 장기적으로 잡을 Pod/Job 단위로 격리하는 선택지(쿠버네티스가 프로세스 정리를 보장)를
  열어 둔다 — 1차 이행 범위는 아님.

- 서버 이식·인증(10절)은 서버 도입 일정([D-08](decisions.md#d-08))에 맞춰 별도 트랙.

**P-B 초기 부트스트랩 상세** — 파이프라인과 독립적이라 규격 협의를 기다릴 필요 없이
기존 콘솔로 바로 시작할 수 있는 선행 작업이다:

배경: 배포 중인 모델은 성능을 신뢰하기 어렵고, 부대별로 모인 **기존 이미지 약 5만 장**이
중복·전처리 미정리 상태로 있다. 파이프라인 첫 가동 전에 이것으로 "신뢰 가능한 베이스
모델"과 "부대별 골든셋"을 만든다.

1. 부대 메타를 붙여 반입한다(부대별 폴더 유지 — 부대 축 원칙은 여기서부터 적용).
2. 기존 품질검사(3계층 중복 검출 — 실데이터로 임계값 검증 완료)로 중복을 제거한다.
   이때 만들어지는 **임베딩 인덱스가 이후 신규 배치의 신규성 선별(4.5)의 기준선**이 된다
   — 레거시와 판박이인 신규 장면은 첫 배치부터 걸러진다.
3. **분할은 유사 그룹 단위로**: 클립 계보가 없으므로 중복 검출이 만드는 근접 유사
   클러스터를 그룹 삼아 train/val/test 를 가른다. 기존 이미지들도 영상 추출본이라 연속
   프레임 중복이 많다 — "프레임 무작위 분할 금지" 원칙(4.5)은 여기에도 동일하게 적용된다.
4. 라벨: 기존 라벨이 있으면 검수, 없으면 초벌 오토라벨 후 검수. 초벌에는 현 배포 모델을
   써도 된다 — 성능 불신 모델이라도 "사람이 고치는 초벌" 용도로는 유효하다.
   **단, 이 단계는 학습 클래스 사전(D-07)이 확정된 뒤에 시작한다** — 세분 목록이 바뀌면
   재라벨이 된다. 1~3단계(반입·중복 제거·그룹화)는 확정 전에도 진행 가능.
5. **부대별 골든셋을 이 5만 장에서 선별·전수 라벨한다** — D-04 작업의 재료가 이미 있다.
6. 베이스 모델을 학습하고 평가 게이트(4.7)를 통과시켜 배포한다. **이 모델이 파이프라인의
   첫 오토라벨 선생(teacher)이다** — 현 배포 모델은 teacher 로 쓰지 않는다.

이후 들어오는 클립 데이터는 이 베이스 위에 월 사이클로 누적된다.
